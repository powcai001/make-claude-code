# 第 00 章：前言

> 📦 **本项目源码**：https://github.com/powcai001/make-claude-code


## 我为什么要写这本书？

如何认真研究 Claude Code 或者 Codex 的时候，事实上，真正让一个大模型变成“能干活的 Agent”的，并不只是模型本身，而是模型外面那一整套 Harness。

模型负责理解、推理和生成；Harness 负责把模型的意图变成真实世界里的动作：调用工具、检查权限、维护上下文、记录任务、恢复错误、协调多个 Agent。换句话说，Agent 的能力并不是凭空出现的，它来自模型能力和工程系统的组合。

```text
Model + Harness = Agent
```

真正理解这件事，或者学习它，最好的方式，是自己从零造一遍。

所以我决定写这本书：一边学习 Claude Code 的核心机制，一边用 Python 写出自己的最小实现，再把每一步的理解、代码和踩坑记录下来。

这本书不是一本“Claude Code 使用教程”，而是一本“我如何从零理解并实现 Agent Harness”的工程笔记。

## 我眼中的 Harness 是什么？

在 `learn-harness-engineering` 里，有一个对我影响很大的观点：强模型仍然会失败。

失败的原因不一定是模型“不够聪明”，很多时候是因为它缺少一个稳定的外部工作系统：任务没有边界，信息没有沉淀，状态不能延续，验证没有闭环，失败之后也没有恢复机制。

这就是 Harness 的价值。

我理解的 Harness，不是“给模型加几个工具”这么简单，而是一套让 Agent 能稳定完成任务的工程系统。它至少包含几类能力：

- **上下文管理**：让 Agent 知道现在该看什么，不该被无关信息淹没。
- **工具系统**：把模型的意图转换成可执行动作，并处理输入、输出和错误。
- **权限边界**：让 Agent 可以做事，但不能无边界地乱做事。
- **状态持久化**：让长任务不会因为一次会话结束就全部丢失。
- **任务与计划**：让 Agent 不只是即时反应，而是能围绕目标推进。
- **验证与观测**：让 Agent 的结果可以被检查、被复现、被改进。
- **多 Agent 协作**：让复杂任务可以被拆分、交接、隔离和汇总。

如果说模型是“脑子”，那 Harness 更像是“工作台、工具箱、流程表、检查清单和团队协作制度”。没有 Harness，模型只能一次性回答；有了 Harness，模型才有机会持续地完成真实任务。

## 为什么叫 Harness？

"Harness" 在英语里的本意是"马具"——套在马身上、连接马车的那套皮带和缰绳。

这个比喻精妙在三个层次：

第一层：力量已经存在。
一匹马不需要 Harness 来变强壮。同样，一个大模型不需要 Harness 来变聪明。
Harness 从不负责增强模型能力——它只负责让已有的能力可被稳定使用。

第二层：方向需要引导。
一匹没有马具的马，只会四处乱跑。
一个没有 Harness 的模型，只会一次性回答——它不知道什么时候该用工具、
什么时候该读文件、什么时候该验证结果、什么时候该停下来。

第三层：边界决定可靠性。
马具控制马的力量边界（拉多少、跑多快、往哪走）。
Harness 控制模型的行动边界（能调哪些工具、能不能写文件、错误后怎么恢复）。

这就是为什么我们不叫它 Framework、Platform 或 Runtime——
那些词描述的是"你建在里面的结构"、"你站在上面的基础"或"被动执行环境"。
而 Harness 描述的是：把已有力量引导到正确方向的控制系统。

但这里有一个反直觉的事实，必须先讲清楚，否则后面所有讨论都会偏。

很多人会想：模型现在还不够好，所以要在它外面套一层东西补它的缺陷；等模型变得足够强，这一层东西就会消失，大家又回到"直接把任务丢给模型"的简单世界。

这个理解听起来合理，但它解释不了一个事实：从早期模型到今天的能力最强的模型，围绕 Claude Code 的 harness 没有变薄，反而变厚了。query loop 变复杂了，权限策略变细了，compact 机制变成熟了，hook 系统变丰富了。如果 harness 只是能力补丁，模型变强应该让补丁变少才对。实际情况正好相反。

原因在于：harness 不是在补模型的短处，而是在承担模型结构上不该承担的那部分工作。就像 CPU 再强也需要操作系统——不是因为 CPU 不够好，是因为调度和持久化这类事本来就不该由 CPU 来做。模型也一样，有些事它做不好不是因为它弱，而是因为它的工作方式从结构上就不适合做这些事：维持连续状态、判断停止条件、对全局一致性负责、独立验证自己的工作。

这意味着一个听起来反直觉、但很自然的推论：模型越强，harness 的必要性反而更高，不是更低。能力弱的模型造成的破坏是局部的、容易被察觉的——它写的代码跑不通、它的回答明显离题。能力强的模型造成的破坏是系统的、难以察觉的——它写出看起来没问题的代码，但引入了一个隐蔽的竞态条件；它做出看起来很合理的架构决策，但违反了你项目里一个它不知道的约束。弱模型让你在第一分钟就发现它不行，强模型让你在一周后才发现它做了什么。

所以这本书里我们要实现的那些机制——query loop、权限、hook、compact、subagent——不是"等模型更强就可以删掉的脚手架"，而是 LLM 这类系统在被嵌入真实工程环境时必须完成的一次职责再分配。会过时的是针对具体弱点的临时补丁，不会过时的是承担结构性分工的基础设施。

## 这本书参考了哪些资料？

这本书主要参考三套资料，但它们在我的项目里承担不同角色。

第一套是 `learn-claude-code`。它是我的实现主线。我会按照它的 20 个机制一步步重写：agent loop、tool use、permission、hooks、todo、memory、subagent、multi-agent、MCP 等。它回答的是：Claude Code 风格的机制可以怎么写出来？

第二套是 `learn-harness-engineering`。它是我的理论主线。它提醒我，Agent Harness 不只是“让模型调用工具”，而是一套让 Agent 能稳定完成任务的工程系统。它回答的是：为什么强模型仍然会失败？为什么需要上下文、状态、任务边界、验证、观测和恢复？

第三套是 `claude-code-system-prompts`。它是我的真实系统对照。我会在彩蛋章节里用它分析真实 Claude Code 的提示词设计，看看我写的简化实现和真实系统之间有哪些相同点、差异和取舍。

所以，这本书不是单纯复刻某一个教程，而是把三件事合在一起：

```text
实现机制 + 理论框架 + 真实系统对照
```

除了上面三套主线资料，写作这本书时我还参考了一些中文社区里对 Harness Engineering 的高质量讨论。下面两篇是其中对我影响最大的，建议配合阅读：

- 《Harness Engineering 的本质是什么？》（情酱，知乎）——它用"模型越强，harness 反而越厚"这个反直觉事实，把 harness 从"能力补丁"重新定义成"结构性分工"。前面"为什么叫 Harness"那一节的最后几段，正是建立在这个视角之上。
- 《从 Claude Code 看 Harness Engineer 的设计》（初级程序员，知乎）——它把 MCP、Skill、Hook、Subagent 这四个机制读成四条 Harness 设计原则，核心一句话：用系统结构保证行为，而不是用语言描述期望行为。

## 这本书不是教程翻译

我会参考现有资料，但不会把它们翻译一遍就结束。

每一章我都会做三件事：

1. 先用自己的话解释：这个机制解决什么问题？
2. 再写一个自己的最小实现：哪怕很简陋，但必须能表达核心思想。
3. 最后记录我踩过的坑：哪里一开始想错了？哪里代码跑不起来？哪里和真实 Claude Code 不一样？

我希望这本书保留“我从不会到会”的过程，而不是伪装成一开始就什么都懂。

真正有价值的，不只是最后的代码，而是中间那些错误、修正和重新理解。

## 这本书写给谁？

这本书主要写给三类读者。

第一类，是已经会写代码，但对 Agent、Tool Use、Memory、Multi-Agent 这些概念还停留在表面的人。你可能知道 Agent 会调用工具，但不清楚工具是怎么注册、怎么分发、怎么加权限边界的。

第二类，是想理解 Claude Code、Cursor、Devin 这类 AI Coding Agent 背后工程结构的人。它们看起来很智能，但真正支撑它们稳定工作的，是一套非常具体的系统设计。

第三类，是想进入 Agent Harness、AI Infra、AI Coding 相关方向的工程师。相比单纯会调 API，我更想展示的是：我能不能把一个 Agent 系统拆开，理解它的机制，再亲手实现出来。

## 这本书怎么读？

本书一共有 20 章正文和 1 章彩蛋章节。

前几章会从最基础的 Agent Loop 开始：

- Agent 为什么是一个循环？
- 工具调用是怎么接进来的？
- 为什么需要权限系统？
- Hooks 为什么是扩展点，而不是把主循环写得越来越复杂？

中间部分会加入规划、记忆、上下文压缩、系统提示词和错误恢复，让单个 Agent 从“能动”变成“能稳定地动”。

后半部分会进入长期任务、多 Agent 协作、任务协议、工作区隔离和 MCP 插件系统。到最后，我们会把这些机制放回一个完整 Harness 里，看它们分别处在系统的哪个位置。

建议阅读方式是：

```text
先读 docs/ 里的章节解释
再运行 code/ 里的对应代码
最后回头看“我踩的坑”和“对照 Claude Code”
```

每章的正文不会贴完整代码，只会展示关键片段。完整实现会放在 `code/` 目录下。

例如：

```bash
python code/s01_agent_loop.py
```

## 我希望读者读完能得到什么？

读完这本书后，我希望你不只是知道几个名词：

- Agent Loop
- Tool Use
- Permission
- Hooks
- Memory
- Context Compact
- Subagent
- MCP
- Multi-Agent

而是能回答更底层的问题：

- 为什么 Agent 需要循环？
- 为什么工具系统不能只是一个 `if else`？
- 为什么权限不是限制能力，而是让能力可控？
- 为什么上下文压缩不是“省 token”，而是长期运行的基础设施？
- 为什么多 Agent 系统的难点不是“多开几个模型”，而是通信、协议、隔离和任务边界？
- 为什么 Claude Code 这类产品，本质上是一套 Harness 工程？

如果你能回答这些问题，就说明你已经不只是“会用 Agent”，而是在理解 Agent 背后的工程系统。

## 我的写作原则

写这本书时，我给自己定了几个原则。

第一，所有概念都要用大白话解释。  
如果一个机制我不能用简单语言讲清楚，说明我还没有真正理解。

第二，代码要小，但要表达核心思想。  
我不会追求一开始就写出完整框架，而是每章只实现一个最小可运行机制。

第三，必须记录真实踩坑。  
工程能力不是体现在“永远不出错”，而是体现在出错之后能定位、修复、总结。

第四，要始终对照真实系统。  
我写的是简化版，但我会不断问自己：这部分在真实 Claude Code 里可能对应哪里？官方为什么会这样设计？
